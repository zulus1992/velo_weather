# 🚴 Прогноз для велосипеда → Telegram (работает без ПК, с Android)

Скрипты берут почасовой прогноз WeatherAPI.com (шаг 1 час; на бесплатном тарифе — 3 суток,
72 точки), сверяют его с правилами `weather_rules.xlsx` (нужно / нормально / можно) и
отправляют короткое сообщение в Telegram.
Бот публикует прогноз по расписанию из `weather_schedule.json`: по умолчанию это **одно
сообщение в день — прогноз на завтра в 09:25 по Минску**. Вердикт и «окна» считаются только
по светлому времени суток: кататься раньше
восхода и после заката нельзя. Восход и закат берутся из того же ответа WeatherAPI (поля
`astro.sunrise` / `astro.sunset` — у каждых суток свои), а если API их не отдал —
считаются офлайн в `sun_times.py`.
Публикация защищена паролем: пока в чат не отправят команду `/password ПАРОЛЬ`, бот молчит.

| Файл | Назначение |
|---|---|
| `get_weather_forecast.py` | почасовой прогноз WeatherAPI.com в плоском виде (`date`, `date_local`, `temp`, `wind_speed`, `wind_speed_kmh`, `condition`, `pop`); восход и закат — из полей `astro` того же ответа |
| `cycling_rules.py` | правила из xlsx + расчёт вердикта и «окон» времени (только между восходом и закатом) |
| `sun_times.py` | тип `Daylight` и офлайн-расчёт восхода/заката (алгоритм NOAA) — запасной вариант, когда API не отдал солнце |
| `send_telegram.py` | отправка в Telegram: пароль `/password`, `--day`, `--hours`, `--sun-source`, `--no-sun`, `--dry-run`, `--reset-auth`, `--find-chat-id`, `--log` |
| `weather_rules.xlsx` | сами правила (температура / ветер км/ч / вероятность осадков %) |
| `telegram_config.example.json` | пример конфига для вариантов B/C и ПК (`bot_token`, `chat_id`, `password`, `api_key`) |
| `weather_schedule.json` | расписание рассылки: когда и какой прогноз публикуется (`time_local`, `weekdays`, `day`) |
| `schedule_slots.py` | расписание в работе: таблица «когда что уйдёт», cron-строки для workflow, сверка `--check` |
| `.github/workflows/weather.yml` | расписание в облаке GitHub — **вариант A** (cron повторяет `weather_schedule.json`) |
| `android_termux_setup.sh` | установка и расписание на самом телефоне (Termux) — **вариант B** |
| `run_weather.sh` | отправка прогноза на телефоне: одно сообщение в день утром (задача Android JobScheduler) |

## Шаг 0. Бот и chat_id (нужен только телефон)

1. Telegram → `@BotFather` → `/newbot` → придумать имя и username → получить токен вида `123456:AA...`.
2. Написать своему боту любое сообщение (бот не может писать первым).
3. Узнать `chat_id` прямо в браузере телефона:
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` → в ответе будет `"chat":{"id":987654321,...}`.

## Шаг 1. Пароль: бот публикует только после `/password ПАРОЛЬ`

Чтобы погоду в чат не мог получить случайный человек (и чтобы бот молчал в чужом чате),
публикация защищена паролем: **пока в чат не отправят команду `/password ПАРОЛЬ`, бот
не публикует ничего** — в логе будет `Чат ... не авторизован`.

1. Придумать пароль и задать его одним из способов (в порядке приоритета):
   * секрет `WEATHER_BOT_PASSWORD` (GitHub Actions и любой планировщик),
   * ключ `"password"` в `telegram_config.json` (Termux, PythonAnywhere, ПК),
   * флаг `--password ПАРОЛЬ` при запуске (виден в истории команд — на ПК лучше не так).
2. Отправить в чат с ботом команду:

   ```
   /password ВАШ_ПАРОЛЬ
   ```

3. Дождаться ближайшего запуска по расписанию (по умолчанию — 09:25 по Минску,
   см. «Расписание рассылки» ниже) или нажать **Run workflow**: бот ответит
   «✅ Пароль принят…» и опубликует прогноз. Дальше пароль присылать не нужно —
   доступ запоминается в `chat_auth.json` (в GitHub Actions — в кэше между запусками).

Важные детали:

* Если бот добавлен в **группу**, Telegram по умолчанию не показывает ему обычные сообщения.
  Либо выключите приватность: `@BotFather` → `/setprivacy` → выбрать бота → **Disable**,
  либо пишите команду с упоминанием бота: `/password@имя_бота ВАШ_ПАРОЛЬ`.
* Команда ищется среди свежих сообщений бота (`getUpdates` отдаёт последние ~24 часа),
  поэтому `/password` нужно отправить не позже, чем за сутки до первого удачного запуска.
* Смена пароля (новый секрет/строка в конфиге) сбрасывает доступ — команду нужно отправить
  заново. Забыть доступы вручную: `python send_telegram.py --reset-auth`.
* В файле `chat_auth.json` хранится только SHA-256 пароля, сам пароль — нет; файл исключён
  из git (`.gitignore`).
* `--dry-run` показывает текст сообщения и ничего не публикует, поэтому работает без пароля.

## Вариант A (рекомендую): GitHub Actions — ПК и телефон не нужны вообще

Работает на серверах GitHub по расписанию, даже если телефон выключен.

1. На github.com создать **приватный** репозиторий, например `weather`.
2. Загрузить в корень репозитория: `get_weather_forecast.py`, `cycling_rules.py`,
   `sun_times.py`, `send_telegram.py`, `weather_schedule.json`, `schedule_slots.py`,
   `weather_rules.xlsx`, `requirements.txt`, `.gitignore`
   и создать файл по пути `.github/workflows/weather.yml`
   (Add file → Create new file → ввести путь целиком, затем вставить содержимое).
   С телефона это удобно делать в мобильном браузере (режим «Версия для ПК»).
3. Settings → Secrets and variables → Actions → **New repository secret**:
   * `TELEGRAM_BOT_TOKEN` — токен из BotFather,
   * `TELEGRAM_CHAT_ID` — ваш chat_id,
   * `WEATHER_BOT_PASSWORD` — пароль для команды `/password` (шаг 1),
   * `WEATHER_API_KEY` — ключ WeatherAPI.com (см. ниже).
4. Вкладка **Actions** → «I understand my workflows, go ahead» → выбрать
   «Прогноз для велосипеда в Telegram» → **Run workflow** (ручная проверка, нажатие
   с телефона; можно выбрать период прогноза: `tomorrow`, `today`, `weekend`, `all`).
5. Через ~20 секунд придёт сообщение в Telegram; при ошибке подробности будут в логе шага.
   Если в логе «Чат ... не авторизован» — отправьте в чат `/password ВАШ_ПАРОЛЬ` и запустите снова.

Дальше всё автоматом: рассылка идёт по расписанию из `weather_schedule.json` —
**одно сообщение в день: 09:25 по Минску, прогноз на завтра**. Cron в
`.github/workflows/weather.yml` повторяет это расписание в UTC.
Полезно: `Actions → нужный запуск → Re-run jobs` — повторить отправку без ПК.
Секреты GitHub маскирует в логах, токен в открытом виде нигде не светится.

### Расписание рассылки: когда и что публикуется

Когда и какой прогноз уходит, описано в одном файле — `weather_schedule.json`
(время **местное**, по умолчанию Минск, UTC+3):

| Слот | Время | Дни | Что публикуется |
|---|---|---|---|
| `утро` | 09:25 | пн-вс | прогноз на завтра (`--day tomorrow`) — одно сообщение в день |

Периоды `today`, `weekend` и `all` никуда не делись: их можно запросить вручную
(**Run workflow** в Actions или флагом `--day` при запуске на ПК/телефоне) либо добавить
вторым слотом в `"slots"` (см. ниже про добавление слота).

Поля слота: `name` (имя), `time_local` (ЧЧ:ММ по местному времени), `weekdays`
(1=Пн … 7=Вс; `"all"` или без ключа — каждый день), `day` (режим прогноза: `today`,
`tomorrow`, `weekend`, `all`), `silent` (`--silent` — без звукового уведомления),
`show_rules` (`--show-rules` — добавить таблицу правил), `enabled` (`false` — слот
остаётся в файле, но ничего не публикует), `about` (пояснение для логов).

* GitHub Actions не умеет читать расписание из файла, поэтому те же моменты продублированы
  cron-строками (UTC) в `.github/workflows/weather.yml`: 09:25 по Минску = `25 6 * * *`,
  а воскресенье в cron — это `0` или `7`. При запуске workflow сам определяет слот по
  `github.event.schedule` и подставляет `--day` (шаг «Определить слот расписания»).
* Посмотреть расписание и сверить файлы:

  ```bash
  python schedule_slots.py --show          # таблица «когда и что уйдёт»
  python schedule_slots.py --check         # cron в workflow == weather_schedule.json
  python schedule_slots.py --cron-lines    # cron-строки для блока on.schedule
  ```

Поменять время рассылки (например, на 19:00):

1. В `weather_schedule.json` поправить `time_local` (или поставить `"enabled": false`).
2. `python schedule_slots.py --cron-lines` → скопировать строки в блок `on.schedule`
   файла `.github/workflows/weather.yml` (та же правка возможна прямо из телефона).
3. `python schedule_slots.py --check` → убедиться, что расписание и workflow совпадают.

Добавить второе сообщение (например, вечернее в 18:00 с прогнозом на завтра) — так же:
добавить объект в список `"slots"` (`"time_local": "18:00"`, `"day": "tomorrow"`), взять
cron-строку из `--cron-lines` и вставить её в `on.schedule`. Для точного времени
в пределах ±10 минут используется вариант B/C (GitHub сам разносит запуски по времени).

Параметры `schedule_slots.py`:

| Ключ | Значение |
|---|---|
| `--show` | таблица «когда и что публикуется» |
| `--cron-lines` | cron-строки для блока `on.schedule` в workflow |
| `--check` | сверить cron в workflow с `weather_schedule.json` (код выхода 1 при расхождении) |
| `--cron "30 3 * * *"` | что публиковать при срабатывании этого cron (в Actions — `github.event.schedule`) |
| `--manual-day today` | период прогноза для ручного запуска (`--cron` без значения) |
| `--github-output FILE` | передать `day` / `silent` / `skip` / `args` в шаг workflow (по умолчанию `GITHUB_OUTPUT`) |
| `--file`, `--workflow` | пути к расписанию и к файлу workflow |


### Где живут секреты и как они подставляются

`${{ secrets.ИМЯ }}` понимает **только сам GitHub Actions и только в файлах workflow**
(`.github/workflows/*.yml`) — в `env:`, `with:` и `run:`. Внутри Python-файлов такая
запись не сработает: интерпретатор увидит обычную строку, и запрос уйдёт с мусорным ключом.

Схема:

* `send_telegram.py` читает доступы из переменных окружения:
  `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `WEATHER_BOT_PASSWORD` (пароль для `/password`),
  а ключ погоды — `WEATHER_API_KEY` (читает его `get_weather_forecast.py`);
* workflow передаёт их в `env:` шага — так секретов в коде нет.

| Секрет GitHub | Что это | Нужен |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота из BotFather | обязательно |
| `TELEGRAM_CHAT_ID` | числовой id чата (у групп отрицательный) | обязательно |
| `WEATHER_BOT_PASSWORD` | пароль для команды `/password ПАРОЛЬ` | обязательно: без него бот ничего не публикует |
| `WEATHER_API_KEY` | ключ WeatherAPI.com (погода) | обязательно для репозитория: `get_weather_forecast.py` берёт ключ из этой переменной или из `--api-key`, в коде ключа нет |

Чтобы ключ погоды не хранился в коде: создайте секрет `WEATHER_API_KEY`, а скрипт прочитает
его из окружения (на ПК ключ можно передать и флагом `--api-key`). Если ключа нет, скрипт
скажет понятное «Не задан ключ WeatherAPI.com: укажите --api-key или задайте переменную
окружения WEATHER_API_KEY».

### Где взять ключ WeatherAPI.com

1. Зарегистрироваться на [weatherapi.com](https://www.weatherapi.com/signup.aspx) — есть
   бесплатный тариф.
2. В личном кабинете скопировать **API key** (строка вида `0123456789abcdef0123456789abcdef`).
3. Положить ключ в секрет `WEATHER_API_KEY` (GitHub Actions), в переменную окружения,
   в `telegram_config.json` (ключ `"api_key"` — для Termux/ПК) или передать флагом `--api-key`.

Бесплатного тарифа хватает: почасовой прогноз на 3 суток (72 точки) — это и «сегодня»,
и «завтра», и выходные. Восход и закат (поле `astro`) приходят в том же ответе на каждые
сутки, поэтому отдельных запросов ради солнца не нужно.

## Вариант B: на самом телефоне (Termux, без облака)

Одно сообщение в день: утром прогноз на завтра — как слот `утро` в `weather_schedule.json`.

1. Поставить **Termux** и **Termux:API** из F-Droid (версия из Play Market не подходит).
2. Скопировать в `~/weather` файлы `get_weather_forecast.py`, `cycling_rules.py`,
   `sun_times.py`, `send_telegram.py`, `weather_rules.xlsx`, `telegram_config.example.json`,
   `android_termux_setup.sh` и `run_weather.sh`
   (например, через Telegram «Избранное» → скачать → `mv /sdcard/Download/<файл> ~/weather/`).
3. Выполнить:
   ```bash
   cd ~/weather && bash android_termux_setup.sh
   ```
4. Скрипт сам: поставит Python и `requests`, создаст `telegram_config.json`
   (впишите токен, chat_id, пароль и ключ WeatherAPI.com — `api_key`:
   `nano ~/weather/telegram_config.json`), покажет прогноз без отправки (`--dry-run`)
   и зарегистрирует ежедневную задачу в Android JobScheduler.
   Затем отправьте в чат `/password ВАШ_ПАРОЛЬ` и проверьте отправку — до команды прогноз
   не публикуется.

Проверка и управление:
```bash
bash ~/weather/run_weather.sh now        # отправить сейчас, не ожидая 09:00
bash ~/weather/run_weather.sh --dry-run  # показать текст, ничего не отправлять
termux-job-scheduler --pending           # список задач
termux-job-scheduler --cancel            # отменить задачу
tail -n 20 ~/weather/weather.log         # лог последних запусков
```

Время задаёт `TARGET_HOUR` в начале `run_weather.sh` (по умолчанию `9` — тот же утренний
слот, что и в `weather_schedule.json`): задача просыпается каждый час, но сообщение уходит
**один раз в день и не раньше 09:00** (отметка об отправке — файл `.last_send`).
Минус варианта: Android сам выбирает точное время фоновой задачи (задержка обычно
до 15–60 минут), а если телефон выключен — сообщение придёт позже. Плюс: данные не покидают телефон.

## Вариант C: PythonAnywhere (облако, одна ежедневная задача бесплатно)

1. Зарегистрироваться на pythonanywhere.com (Free).
2. Files → загрузить `get_weather_forecast.py`, `cycling_rules.py`, `sun_times.py`,
   `send_telegram.py`, `weather_rules.xlsx`, `telegram_config.json` (токен, chat_id, пароль).
3. Bash console: `pip3 install --user requests`.
4. Tasks → задать время (по умолчанию там UTC, т.е. 06:25 = 09:25 по Минску) и команду из
   `weather_schedule.json` (одно сообщение в день, слот `утро`):
   `python3.10 send_telegram.py --day tomorrow`.
5. Отправить в чат `/password ВАШ_ПАРОЛЬ` и нажать **Run now** для проверки.

## Параметры `send_telegram.py`

| Ключ | Значение |
|---|---|
| `--day today / tomorrow / weekend / all` | какой период описывать (по умолчанию `tomorrow` — прогноз на завтра) |
| `--hours 7-22` | резервный интервал часов, если восход и закат неизвестны (`0-24` — круглосуточно) |
| `--sun-source auto / api / calc` | откуда брать восход и закат. `auto` (по умолчанию) — поля `astro` (`sunrise`/`sunset`) из ответа WeatherAPI, а если их нет — офлайн-расчёт; `api` — только данные API (без расчёта); `calc` — только собственный расчёт |
| `--forecast-file FILE` | взять прогноз из сохранённого ответа WeatherAPI (например, для `--dry-run` без сети); восход и закат берутся из того же файла |
| `--api-key КЛЮЧ` | ключ WeatherAPI.com: аргумент → `WEATHER_API_KEY` → ключ `"api_key"` в `telegram_config.json` |
| `--no-sun` | не ограничивать катание восходом и закатом: вердикт считается по `--hours` |
| `--show-rules` | добавить в сообщение строки правил (`нужно / нормально / можно`) |
| `--city Minsk` (или `--lat/--lon`) | город прогноза |
| `--token`, `--chat-id`, `--config` | доступы: аргумент → переменные `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` → `telegram_config.json` |
| `--password ПАРОЛЬ` | пароль доступа: аргумент → `WEATHER_BOT_PASSWORD` → `"password"` в конфиге (без пароля бот ничего не публикует) |
| `--auth-file FILE` | где помнить открытые доступы (по умолчанию `chat_auth.json` рядом со скриптом) |
| `--reset-auth` | забыть доступы чатов: публикация снова потребует `/password ПАРОЛЬ` |
| `--dry-run` | показать сообщение, ничего не отправлять (удобно проверять правки, пароль не нужен) |
| `--find-chat-id` | вывести chat_id по последним сообщениям боту |
| `--log FILE` | дописывать результат в лог-файл (нужно при запуске по расписанию) |
| `--silent` | отправить без звукового уведомления |

## Параметры `get_weather_forecast.py`

| Ключ | Значение |
|---|---|
| `--city Minsk` (или `--lat/--lon`) | город прогноза (параметр `q` WeatherAPI) |
| `--days N` | сколько суток запросить (1…14; на бесплатном тарифе реально 3) |
| `--api-key КЛЮЧ` | ключ WeatherAPI.com: аргумент → `WEATHER_API_KEY` из окружения |
| `--lang ru` | язык описаний погоды (`lang=ru`) |
| `--tomorrow` | только почасовые точки на завтра (24 часа, шаг 1 час) |
| `--daily` | агрегированная сводка по суткам (мин/макс температуры, ветер, осадки, светлое время) |
| `--sun` | восход и закат по суткам прогноза (поля `astro` WeatherAPI) |
| `--sun-source auto / api / calc` | источник солнца: `auto` (API, иначе расчёт), `api` (только API), `calc` (только офлайн-расчёт) |
| `--from-file FILE` | читать сохранённый ответ API из файла вместо запроса к сети |
| `--save-raw FILE` | сохранить сырой ответ API (в нём и `astro`) для `--from-file` |
| `--out FILE`, `--indent N` | куда писать результат и с каким отступом JSON (`--indent 0` — компактно) |

## Как считается вердикт

* Правила читаются из `weather_rules.xlsx`: `нужно` (t > 18 °C, ветер < 4 км/ч, осадки 0 %),
  `нормально` (t > 12, ветер < 10, осадки < 10 %), `можно` (t > 5, ветер < 14, осадки < 20 %).
  Проверяется от лучшей строки к худшей — побеждает первая подошедшая.
* Оценка идёт по светлому времени суток: **кататься раньше восхода и после заката нельзя**.
  Восход и закат приходят из ответа WeatherAPI (блок `astro` внутри каждых суток прогноза,
  поля `sunrise` / `sunset`):
  * `forecast.forecastday[].astro.sunrise` / `.sunset` — значения на каждые сутки прогноза
    (на бесплатном тарифе это 3 суток, включая сегодня и завтра);
  * если нужных суток в ответе нет, берутся ближайшие известные, и в сообщении это помечено
    «данные за ДД.ММ» (разница — минуты в день, для правила «не кататься в темноте» это
    несущественно);
  * если API не отдал солнце вовсе, а `--sun-source auto`, сутки считаются офлайн-расчётом
    `sun_times.py` по координатам и часовому поясу города (`--sun-source api` запрещает расчёт,
    `calc` — наоборот, требует только его);
  * пустые или бессмысленные поля `astro` (полярные широты) пропускаются: при
    `--sun-source auto` эти сутки считает `sun_times.py`, при `api` они остаются без солнца.
  В сообщении время выводится строкой `• светлое время: 06:58–19:03 (WeatherAPI)`,
  а окна обрезаются по восходу и закату.
* Точки прогноза идут с шагом 1 час, поэтому окно считается точно: при восходе 06:58 часовое
  окно `06:00–07:00` учитывается как `06:58–07:00`.
* Если данных о солнце нет (или включён `--no-sun`), используется резервный
  интервал `--hours 7-22`, поэтому дождливая ночь не превращает день в «можно».
* `pop` из WeatherAPI — вероятность осадков 0…1 (максимум из `chance_of_rain` и `chance_of_snow`), в правилах сравнивается как проценты.
* Ветер в API приходит в км/ч (`wind_kph`), в правилах тоже км/ч, но точка прогноза хранит и `wind_speed_kmh`, и `wind_speed` (м/с) — на случай других расчётов.

## Частые вопросы и ошибки

| Симптом | Что делать |
|---|---|
| Сообщение не приходит | Проверить, что написали боту первым; проверить токен и chat_id; смотреть лог запуска (Actions / `weather.log` в варианте B) |
| `HTTP 400 ... chat not found` | Неверный `chat_id` или боту не писали: Telegram → напишите боту `/start` → взять id из `.../getUpdates` → **перезаписать** секрет `TELEGRAM_CHAT_ID` (секреты GitHub не показываются, только перезапись) |
| `401` | Токен отозван или скопирован с ошибкой — перевыпустить в BotFather |
| `Город не найден` (`error.code 1006`) | Проверить `--city` (например, `Minsk`) или передать координаты `--lat` и `--lon` |
| Прогноз «пустой» на дальние сутки | Бесплатный тариф WeatherAPI даёт 3 суток вперёд: дальние дни появятся позже (для «сегодня», «завтра» и выходных этого хватает) |
| Расписание в GitHub сработало с задержкой 10–30 минут | Норма для GitHub Actions; для точного времени используйте вариант B/C |
| Сообщение приходит не ровно в 09:25, а на 10–30 минут позже | Та же задержка GitHub Actions; время рассылки задано в `weather_schedule.json`, а для точности до минут нужен вариант B/C |
| Хочу поменять время рассылки | Правьте `time_local` в `weather_schedule.json`, затем `python schedule_slots.py --cron-lines` → вставить строки в `on.schedule` в `.github/workflows/weather.yml` и проверить `python schedule_slots.py --check` |
| Хочу два сообщения в день (например, утром и вечером) | Добавьте объект в `"slots"` в `weather_schedule.json` (например, `"time_local": "18:00"`, `"day": "tomorrow"`), возьмите строки из `python schedule_slots.py --cron-lines` и вставьте их в `on.schedule`, затем `python schedule_slots.py --check` |
| Хочу, чтобы рассылка молчала (например, в отпуске) | Поставьте слоту `"enabled": false` в `weather_schedule.json` — workflow всё равно запустится по cron, но шаг отправки пропустится |
| В логе `Предупреждение: cron "..." не описан в weather_schedule.json` | Cron в workflow разошёлся с расписанием: обновите строки через `python schedule_slots.py --cron-lines` (или проверьте `python schedule_slots.py --check`) |
| Пришёл не тот прогноз (например, на сегодня вместо завтра) | Слот и режим заданы в `weather_schedule.json` (`day`: `today` / `tomorrow` / `weekend` / `all`); при ручном запуске период выбирается в **Run workflow** |
| Восход/закат в сообщении отличаются от другого сайта на 1–3 минуты | Значения берутся из WeatherAPI (поля `astro.sunrise`/`sunset`), а сайты расходятся между собой на столько же (разные высота над морем и рефракция). Если включён `--sun-source calc`, время считает наш офлайн-расчёт NOAA — он чуть консервативен: восход позже, закат раньше |
| В логе `Не задан ключ WeatherAPI.com` | Ключ не передан: добавьте секрет `WEATHER_API_KEY` (Actions), переменную окружения `WEATHER_API_KEY`, ключ `"api_key"` в `telegram_config.json` или флаг `--api-key` |
| В логе `ключ API недействителен` (`error.code 2006`) / `закончился лимит вызовов` (`2007`) | Проверить ключ в кабинете weatherapi.com, при необходимости выпустить новый и перезаписать секрет `WEATHER_API_KEY` |
| В сообщении «данные за ДД.ММ» рядом со светлым временем | Суток с восходом/закатом в ответе нет, и взяты ближайшие известные (у бесплатного тарифа солнце есть на все 3 суток — так бывает только на границе окна прогноза) |
| Хочу видеть, откуда взято светлое время | В сообщении это подпись в строке светлого времени (`WeatherAPI` или `расчёт офлайн`), в логе — строка «Восход и закат: …». Офлайн-проверка: `--forecast-file response.json` (файл сохраняет `--save-raw`) |
| Хочу вердикт без ограничения по светлому времени | Добавьте `--no-sun` (тогда работает резервный интервал `--hours 7-22`) |
| Бот молчит, в логе `Чат ... не авторизован` | Отправьте в чат `/password ВАШ_ПАРОЛЬ` и запустите снова; проверьте, что пароль задан (`WEATHER_BOT_PASSWORD` / `"password"` в `telegram_config.json`) |
| В группе команда `/password` не доходит до бота | Telegram скрывает от ботов обычные сообщения: `@BotFather` → `/setprivacy` → выбрать бота → **Disable**, либо пишите `/password@имя_бота ВАШ_ПАРОЛЬ` |
| В логе `Не задан пароль бота` | Пароль не передан: добавьте секрет `WEATHER_BOT_PASSWORD` или ключ `"password"` в `telegram_config.json` — без пароля публикации нет |
| В логе `Пароль в команде /password не совпадает` | В чат отправлен другой пароль, чем задан в секрете/конфиге — исправьте пароль или отправьте команду с верным |
| Пароль верный, но публикации нет | Команда ищется в свежих сообщениях (~24 часа): отправьте `/password` и запустите workflow сразу. Доступ помнится в `chat_auth.json` (в Actions — в кэше), сбросить: `--reset-auth` |

### Если в Actions появилось `Bad Request: chat not found`

1. Откройте Telegram и напишите своему боту `/start` — бот не может писать первым, без этого чата для него «не существует».
2. Запустите workflow: в логе шага «Диагностика: имя бота и доступные chat_id» появится
   `Бот: @ваш_бот (id ...)` и строки вида `chat_id: 987654321  (Иван)`.
3. Settings → Secrets and variables → Actions → `TELEGRAM_CHAT_ID` → **Update** — вставить id
   **числом** (без кавычек, без `@username`, без пробелов; для группы/канала id отрицательный).
4. Снова **Run workflow** — сообщение должно прийти.

Скрипт сам подчищает пробелы и кавычки вокруг токена/chat_id и заранее сообщает, если вместо id
передан `@username`.

## Локальный запуск (по желанию, на ПК)

```powershell
$env:WEATHER_API_KEY = "ваш-ключ"                 # ключ WeatherAPI.com (или --api-key, или "api_key" в telegram_config.json)
python send_telegram.py --dry-run                 # проверить текст (пароль не нужен)
python send_telegram.py --day tomorrow            # отправить (нужен пароль и /password в чате)
python send_telegram.py --reset-auth              # забыть доступы чатов
python send_telegram.py --sun-source api          # восход и закат только из данных WeatherAPI
python schedule_slots.py --show                   # когда и что публикуется
python schedule_slots.py --check                  # cron в workflow == weather_schedule.json
python schedule_slots.py --cron "30 3 * * *"      # что отправит этот слот (как в Actions)
python get_weather_forecast.py --tomorrow         # только данные прогноза
python get_weather_forecast.py --sun              # восход и закат по суткам (из данных API)
python get_weather_forecast.py --daily            # сводка по суткам: мин/макс температуры, ветер, осадки, солнце
python get_weather_forecast.py --save-raw response.json   # сохранить ответ API (в нём и солнце)
python sun_times.py --days 5                      # запасной офлайн-расчёт восхода и заката
```

Проверить вердикт без сети — по сохранённому ответу API:

```powershell
python get_weather_forecast.py --save-raw response.json
python send_telegram.py --dry-run --forecast-file response.json
```

Для запуска на ПК скопируйте `telegram_config.example.json` в `telegram_config.json`
и заполните `bot_token`, `chat_id` и `password`, затем отправьте боту в чат
`/password ВАШ_ПАРОЛЬ` — без этого погода не публикуется.
